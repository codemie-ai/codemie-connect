- Stale top-of-file comment in `runner.rs`: the comment still reads "Windows: commands run via `powershell.exe -NoProfile -NonInteractive -Command`" but the code was changed to `cmd.exe /c cmd_str`; any developer adding a Windows command string will write PowerShell syntax expecting it to work and get silent failures — `src-tauri/src/commands/runner.rs` hunk replacing `shell_cmd`

- `tauri.conf.json` bundles `codemie.cmd` at destination path `"bin/codemie.cmd"` (a subdirectory of `resource_dir`), but `inject_bundled_bin_path` probes `resource_dir` root via `d.join("codemie.cmd")` — the probe never matches the bundled shim on the `resource_dir` fallback branch, so PATH injection silently fails on Windows whenever `current_exe()` parent also misses the file — `src-tauri/tauri.conf.json` hunk `+resources` / `src-tauri/src/commands/pathman.rs` `inject_bundled_bin_path`

- `inject_bundled_bin_path` failure is handled in `lib.rs` with `eprintln!("{e}")`, which is swallowed entirely in a packaged Tauri app (no stdout/stderr visible to the user); PATH injection can fail without any user-visible or in-app-log diagnostic — `src-tauri/src/lib.rs` hunk `if let Err(e) = commands::pathman::inject_bundled_bin_path(...)`

- `probe_detects_codemie_cmd_shim` test never calls `probe()` or `inject_bundled_bin_path()`; it creates a file and immediately calls `.exists()` on the known path — a tautology that will pass even if `candidate_bin_names()` stops listing `"codemie.cmd"` — `src-tauri/src/commands/pathman.rs` `tests_windows_probe` block

- `download_to_file` issues `reqwest::get(url)` with no timeout configured; a slow or non-responsive server hangs the Git-for-Windows download (and therefore `install_git_clt`) indefinitely — `src-tauri/src/commands/installer.rs` `download_to_file`

- When the Git-for-Windows installer process exits with a non-zero code the `install_git_clt` function emits a tick event but does NOT return `false`; it falls through to the 5-minute polling loop, which will timeout silently — the user sees "Installer exited with code …" and then 5 minutes of waiting with no recovery path — `src-tauri/src/commands/installer.rs` `install_git_clt` Windows `Ok(s) if !s.success()` arm

- `ui/handlers.js` removes steps `'1.2'` and `'1.2.1'` entirely, leaving the step sequence jumping from `'1.1.1'` directly to `'1.3'`; if any orchestration, progress display, or validation code iterates step IDs numerically or checks for their existence, the gap causes an unresolvable step reference with no comment indicating the gap is intentional — `ui/handlers.js` hunk removing `'1.2'` and `'1.2.1'`

- `run_self_update` on Windows: when `node_exe_path.exists()` is false (empty `PathBuf` from a failed `resource_dir()` call) and `inject_bundled_bin_path` also failed silently, the fallback `capture("codemie self-update", None)` exits with code 127; the resulting error message ("codemie self-update failed (exit 127): …") gives no indication whether the root cause is a missing sidecar, a failed PATH injection, or an actual CLI error — `src-tauri/src/commands/runner.rs` `run_self_update` Windows branch

- `apply_resolved_shell_path()` is called immediately before `inject_bundled_bin_path()` in `lib.rs`; if `apply_resolved_shell_path` also calls `std::env::set_var` internally, both calls happen inside the Tauri `setup()` closure where the Tokio async runtime (and potentially internal Tauri background threads) may already be running, making the `SAFETY` comment's "no thread is spawned" assertion unverified for the first call as well as the second — `src-tauri/src/lib.rs` setup closure ordering
