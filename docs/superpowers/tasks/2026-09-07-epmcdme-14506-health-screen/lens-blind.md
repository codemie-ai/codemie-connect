- `runHealthCheck` (ui/renderer.js, added block after line ~314) has no try/catch around `bridge.runner.runStream('codemie doctor', ...)`; if the doctor process fails to spawn or the stream promise rejects, the Health view is left stuck on `showLoading`'s "Checking…" state forever. Worse, `healthChecked` is already flipped to `true` in the `boot()` click handler (ui/renderer.js ~line 350) before `runHealthCheck()` is invoked, so the auto-run-once guard prevents any automatic retry on a later visit to the tab — the user has no recheck button (it was never rendered) and no way out short of restarting the app.
- No guard against overlapping invocations of `runHealthCheck`: the existing codebase has a `installRunning` busy-flag pattern (visible as unchanged context at ui/renderer.js ~line 166) specifically to prevent a second concurrent run from stepping on the first, but "Check everything again" (`onRecheck: runHealthCheck` in ui/renderer.js ~line 331) has no equivalent — rapid double-clicks or a recheck racing the initial auto-run can fire two `runStream` calls that both eventually call `renderHealth(views.health, ...)`, with whichever resolves last winning regardless of which check is actually current.
- `doctor-parse.js`'s hint detection is brittle: `^\s{6}(.+)$` requires exactly six leading spaces (ui/doctor-parse.js line ~195). Any drift in the CLI formatter's indentation (a hint that wraps to two lines, uses a tab, or is indented by 5/7 spaces) silently produces a record with `hint: undefined` rather than surfacing an error — the row then renders as failed with no remedy text and no action, with nothing pointing at the real cause.
- `doctor-groups.js`'s `failing = items.find(...)` (line ~149) only ever surfaces the first failing item in a multi-line check (e.g. `Agents` has two detail lines in the fixtures). If a check reports two distinct failures, only the first's hint/action is shown; the second is silently absorbed into the aggregate `fail` status with no visible remedy. The runtime-group collapse (`RUNTIME_NAMES` merged into one "Everything CodeMie needs to run is included" row, lines ~140-146) has the same effect at a larger scale: if `Npm` fails and `Python` passes, the single merged row shows `fail` with no `remedyText` or `action` at all (the runtime row is pushed without a `remedyText`/`action` field), leaving the user with a red row and zero guidance on which of the four runtime checks actually failed.
- `GROUP_BY_NAME` and `DEEP_LINKS` (ui/doctor-groups.js lines ~117-126) are closed, hardcoded maps. Any doctor check name not already listed silently falls into `GROUP_BY_NAME[name] || 'codemie'` (line ~155) with no deep link and no warning — a future check added to the CLI's output would be misclassified into the wrong screen section with no error or log line indicating it wasn't accounted for.
- `spawn_open`'s Windows branch (src-tauri/src/commands/logger.rs lines ~44-53) builds `cmd /c start "" <path>` and passes the resolved log path as a raw argument. The path is derived from `USERPROFILE` via `log_dir_with`/`log_dir` (lines ~24-27) with no validation of its contents; if that environment variable (or the constructed path) contains characters meaningful to `cmd.exe` (`&`, `|`, `%VAR%`, etc.), the command could behave unexpectedly instead of simply opening the log file. The comment only explains the empty-string window-title argument, not any protection against metacharacters in the path itself.
- Both `log_dir_with` variants fall back to an empty string when `HOME`/`USERPROFILE` is unset (`unwrap_or_default()`, lines ~21-27), silently yielding a root-relative path such as `/Library/Logs/CodeMie` or `\AppData\Local\CodeMie\Logs`. `ensure_log_readable` (lines ~33-37) then just reports a generic "log file not found or unreadable" for that path, giving the user no indication that the actual problem is a missing environment variable rather than a missing log.
- `ensure_log_readable` followed by `spawn_open` (src-tauri/src/commands/logger.rs, `open_log` at lines ~60-69) has a check-then-act gap: existence/readability is verified with `File::open`, then a separate OS process is spawned moments later to open the same path. If the log file is deleted, rotated, or replaced in between (log writes happen concurrently from `write_line`), the "readable" check passed but the actual open can still fail silently from the user's perspective (the spawned OS handler, not this code, would report or swallow that failure).
