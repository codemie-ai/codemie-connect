# Milestone 1 — implementation test and evidence contract

**Status: planned tests, not implementation results.** Current checks are recorded separately in [BASELINE-VALIDATION.md](BASELINE-VALIDATION.md). Approval of the plan does not turn any future case into PASS.

The required milestone set is **66 task scenarios + 16 legacy regression scenarios = 82 scenario groups**, with data variants listed below. A scenario group may contain several checks or operating-system executions. Each implementation task runs its own scenarios, affected earlier scenarios and all relevant legacy gates. Task 4 runs the whole milestone bar.

## Execution modes and test data

| Mode | What it proves | What it cannot substitute for |
|---|---|---|
| U — unit/property tests | Pure rules, state machines, date conversion, migrations, retry/lease transitions and output validation. Rust + existing node:test conventions. | Native UI, OAuth, real OS delivery or provider behavior. |
| I — native service integration | Production WorkspaceCore/repository/Graph adapters against a local controlled HTTP service, real SQLite and a controlled clock, using isolated test data. Fault injection can cut responses, return 429/403/410/5xx and reorder completion. | A real tenant or live Graph permissions. |
| B — browser UI integration | Real view modules in a browser, controlled IPC bridge and deterministic data; search/filter/navigation/themes/accessibility. | Tauri IPC, WKWebView/WebView2, credential stores, OS notifications. Call it browser integration, not native E2E. |
| N — native fixture E2E | A freshly built Tauri test application, real IPC and repository, fixture transport at the native service boundary, actual window/tray/notification APIs. On macOS use accessibility/computer use and app-emitted test evidence. | Live OAuth/Graph acceptance. |
| C — connected native E2E | The freshly built application, system browser, shared Entra registration, real Graph and owned test resources. Verify the provider/recipient side independently. | Windows execution when only run on macOS, or vice versa. |
| P — packaged/upgrade E2E | Actual app/installer artifact, production identifier/update paths, installed in an isolated OS user/VM; fresh and upgrade checks. | Source build or a static HTML server. |

Native fixtures and clock/network overrides must be test-only, isolated and rejected in production builds. No mocking `window.__TAURI__.invoke` in an N/C/P result. Use a distinct QA application/credential namespace for development; qualification candidates preserve the real production identifier in a disposable environment. Do not repurpose the developer's real CLI configuration or Echo directory.

**OS:** macOS WKWebView and Windows WebView2 are independent gates. Current Tauri WebDriver support is Windows/Linux, not macOS; use native macOS accessibility/computer-use plus instrumented non-destructive app checks, and tauri-driver/WebView2 where supported on Windows. [Tauri documentation](https://v2.tauri.app/develop/tests/webdriver/). OS notification tests use installed artifacts where required by the platform, not just `cargo run`. [Notification platform details](https://v2.tauri.app/plugin/notification/).

**Fixtures:** default Personal workspace + Project A/Project B; account A and account B with disjoint tenant/account IDs; mail Inbox/Sent and moved/deleted/edited messages; 1:1/group/meeting chats including own messages, mentions, automated senders, quoted forwards, HTML injection attempts and duplicates; calendar all-day/overnight/recurring/exception/cancelled events across Europe/Kyiv, Europe/London and America/New_York DST boundaries; 10,000 source items/1,000 events for performance. Retain synthetic data only.

**Live data:** a dedicated organization QA account approved for the same CodeMie public client, a second account for switch/isolation, a QA mailbox recipient and pre-created Teams chat controlled by the tester. Use `CM-CONNECT-M1-<run-id>` markers. No real customer/user conversations enter evidence. Record hashed resource IDs, counts, statuses and redacted screenshots. A live send test uses an explicitly owned recipient and its expected body; no unapproved sends to other people. Consent/tenant configuration is handled by the account/tenant owner when required, never silently bypassed.

## Quantitative and operational acceptance

- Record host OS/build, CPU/RAM/display scale, source revision/dirty status, Rust/Node/CLI versions, app artifact SHA-256, execution mode and fixture version for every report.
- Initial targets on an identified SSD/16 GB reference machine: usable cached shell ≤2 s warm / ≤4 s cold at p95 of 30 runs; first page of 100 Inbox rows ≤150 ms repository time / ≤300 ms native UI end-to-end; critical acknowledgement and installer input feedback ≤250 ms under queue load. Reassess only with recorded evidence and an explicit disposition.
- With app awake and service healthy, newly eligible source detected within the configured polling interval + 30 s (default 90 s foreground / 330 s background); surface actual last sync and retries. Native reminders submit within 15 s of due time while awake; actual OS display is observed separately. Never promise delivery while asleep/quit or through OS DND.
- Soak: at least 8 hours mixed foreground/background use with ≥3 sleep/wake cycles and controlled network interruptions; no duplicated unique job keys, no lost confirmed mutations, no leaked-account results, no unbounded queue/listener/memory growth. Capture beginning/end resource samples and unresolved failures.
- Existing gates: repository-root `npm test`; from `src-tauri/`, `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`. Run repository platform build scripts with their artifact assertions. Native smoke and the repaired, safety-verified detection probe are additional evidence, not substitutes for installation/Graph E2E.
- Existing platform-only skipped tests remain SKIPPED on the wrong OS; run them on the correct OS. A test harness cannot convert SKIPPED to PASS because the feature looks right in Chromium.

## Evidence format and task closure

Each case records `case_id`, parameter/OS/mode, source/build identity, prerequisites, steps actually executed, expected result, observed result, PASS/FAIL/BLOCKED/SKIPPED/N/A, sanitized proof, cleanup and defect link. Do not retain user names, raw conversations, auth URLs/codes or tokens. Export only redacted test data. Keep fixture runs and live-tenant results in separate sections.

At each task's completion: rebuild → run required unit/service checks → run actual native cases and applicable live cases → review visuals → run affected legacy matrix → fix defects and rerun those paths → publish a result report. Do not broaden/repeat successful unrelated checks without a change or unresolved concern. Task 4 performs the planned complete regression/qualification pass.

**Stop conditions:** any security/account leak, lost confirmed state, duplicate unreviewed send, broken installer, data corruption or P0/P1 blocks closure. Unavailable account consent, OS execution or signing is a named BLOCKED gate, never assumed success. Functional development can be reviewed incrementally with explicit limits; the milestone is not declared fully qualified until its mandatory native/live/platform gates have actually passed.
